# Сервис геопланирования 

Модуль распределяет визиты к точкам (клиентам, магазинам) по рабочим дням
месяца, группирует визиты каждого дня в компактные кластеры
(≤ `max_points_per_cluster` точек) и строит порядок обхода внутри кластера.
Результат — CSV-таблицы и интерактивная HTML-карта.

---

## Быстрый старт

```bash
pip install -r requirements.txt
python run.py                 # data/data.csv -> outputs/
python run.py --open-map      # то же + открыть карту в браузере
python -m pytest -q           # тесты (критерии приёмки ТЗ)
```

Параметры командной строки:

| Параметр | По умолчанию | Смысл |
|---|---|---|
| `--data` | `data/data.csv` | входной CSV |
| `--output` | `outputs` | папка результатов |
| `--days` | 22 | рабочих дней в месяце (visit_day = 1..N) |
| `--max-points` | 12 | максимум точек в кластере (ТЗ: 8–12) |
| `--clusters-per-day` | 2 | сколько кластеров менеджер проходит за день |
| `--seed` | 42 | seed кластеризации |
| `--distance` | `osrm` | `osrm` — по дорогам (OSRM, с кешем); `haversine` — по прямой, офлайн; `road` — по локальному графу GraphML |
| `--graphml` | `cache/volga_graph.graphml` | граф для `--distance road` |
| `--no-depot` | — | не начинать маршруты из центра города |
| `--no-map` | — | не строить карту |
| `--straight-lines` | — | линии на карте прямыми (без запросов к OSRM) |

Код выхода `0` означает, что все обязательные проверки плана пройдены.

### Использование из Python / ноутбука

```python
from src import PlannerConfig, run_pipeline

out = run_pipeline("data/data.csv", PlannerConfig(working_days=22),
                   output_dir="outputs")
out["result"].schedule      # итоговая таблица
out["result"].checks        # проверки по критериям приёмки
```

## Входные данные

| Поле | Тип | Обязательно | Описание |
|---|---|---|---|
| `point_id` | string | да | уникальный идентификатор |
| `latitude` (`lat`) | float | да | широта |
| `longitude` (`lon`, `lng`) | float | да | долгота |
| `visits_per_month` (`n_visits`) | int | да | визитов в месяц, из `allowed_visits` (по умолчанию 1, 2, 3, 4) |
| `manager` | int | нет | менеджер; если колонки нет или значение пустое, используется `default_manager` (0) с предупреждением в логе |

**Валидация.** Строки не исправляются молча. Некорректная строка
попадает в `outputs/rejected_rows.csv` с номером строки CSV и причиной:
пустые поля, нечисловые координаты, координаты вне диапазона или (0, 0),
нецелое или недопустимое `visits_per_month` (1.5 и 5 отклоняются, а не
округляются и не обрезаются), дубликат `point_id`.

## Алгоритм

Каждый менеджер планируется отдельно.

### 1. Кластеризация: KMeans с ограничением ёмкости (`clustering.py`)

Точки менеджера делятся на *территории* — компактные группы
≤ `max_points_per_cluster` точек.

* Число кластеров вычисляется автоматически:
  `k = ceil(n / (max_points × fill_ratio))`. При `fill_ratio = 0.9`
  остаётся запас, и кластеры не растягиваются ради заполнения.
* Центры инициализирует обычный KMeans (seed фиксирован).
* Шаг назначения решается как задача о назначениях
  (`scipy.optimize.linear_sum_assignment`): у каждого центра ровно
  `max_points` мест. Поэтому ограничение размера **гарантировано
  построением**, а не проверкой после факта.
* Координаты проецируются в километры, чтобы евклидово расстояние в
  KMeans было корректным: градус долготы на широте 56° ≈ 62 км, а градус
  широты ≈ 111 км.

**Почему не DBSCAN (как в v2).** Там `eps` переводился из км в *градусы*
(`eps_km / 111.32`), хотя метрика `haversine` ожидает *радианы*.
Фактический радиус был около 1400 км, и все 633 точки попадали в один
кластер, который затем дробился KMeans и склеивался эвристиками. DBSCAN не
ограничивает размер кластера, поэтому для задачи «≤ 12 точек»
естественнее метод с ограничением ёмкости.

### 2. Распределение визитов по дням (`schedule.py`)

Точке с `N` визитами за `D` рабочих дней назначаются дни
`p + round(k·D/N)`, k = 0..N−1, где `p` — первый день её территории.
Для D = 22:

| N | смещения | интервал |
|---|---|---|
| 1 | 0 | — |
| 2 | 0, 11 | ровно полмесяца |
| 3 | 0, 7, 15 | ≥ 7 дней |
| 4 | 0, 6, 11, 17 | ≥ 5 дней |

Интервал между визитами всегда ≥ `floor(D/N)`.

Территория «переезжает» по смещениям. В день `p` посещаются все её точки,
в день `p + 11` — только точки с 2+ визитами. Каждый такой выезд —
**кластер дня**. Он является подмножеством компактной территории, поэтому
тоже компактен и укладывается в лимит.

Первый день `p` каждой территории выбирается так:

1. **Жадно.** Сначала ставятся территории с самым поздним последним визитом
   и самые долгие. Для каждой берётся день с минимальным пиком загрузки
   среди затронутых дней при лимите `max_clusters_per_manager_per_day`.
   Загрузка дня оценивается по цепочке «старт → кластер 1 → кластер 2 →
   старт».
2. **Локальный поиск.** Территории переносятся на другие дни и
   обмениваются днями, пока уменьшается сумма квадратов длительностей
   дней. Это сглаживает пики и сводит соседние территории в один день.

**Визиты не теряются.** Если территорию некуда поставить, число территорий
уменьшается (они становятся плотнее), и попытка повторяется. Если места
нет и после этого, визиты записываются в `outputs/unassigned.csv` с
причиной. Заранее в лог выводится загрузка: требуемые визиты против
ёмкости `D × кластеров_в_день × max_points`.

### 3. Маршрут (`routing.py`)

`build_route` строит маршрут методом «ближайший сосед» от точки старта
(центр Нижнего Новгорода, `depot`), затем улучшает его алгоритмом **2-opt**.
Тест сравнивает результат с полным перебором: разница не больше 5 %.
Кластеры одного дня выстраиваются в цепочку: второй кластер начинается с
последней точки первого, и порядок кластеров выбирается кратчайший.

### 4. Расстояния (`distances.py`)

* `osrm` (по умолчанию в `run.py` и ноутбуке) — расстояния **по дорогам**
  через OSRM Table API. На каждый день менеджера отправляется один запрос
  матрицы (все точки дня и старт), дальше порядок обхода и перебор порядка
  кластеров считаются по кешу. Ответы сохраняются в
  `cache/osrm_table_cache.json`: первый запуск на `data.csv` занимает около
  2 минут, повторный идёт без сети за ~10 секунд и даёт идентичный
  результат. Если сервер недоступен, пара считается по прямой × 1.3 и
  попадает в счётчик «по прямой» в логе и `report.json`. Для работы без
  публичного сервера можно поднять локальный OSRM и передать его адрес в
  `OsrmDistance(base_url=...)`.
* `haversine` (по умолчанию в `PlannerConfig` и тестах) — по прямой, без
  сети, для оценки времени умножается на коэффициент извилистости 1.3. Это
  заметно занижает пробег: на `data.csv` обход кластеров по дорогам в
  1,7 раза длиннее, чем по прямой.
* `road` — кратчайший путь по графу OSM (GraphML). Ближайший узел ищется
  KD-деревом, пути — алгоритмом Дейкстры от каждой точки сразу до всех
  точек кластера. Если пара не связана в графе, берётся прямая × 1.3.
  Доля таких пар **выводится в лог и `report.json`**, поэтому всегда видно,
  какой источник фактически использовался. Кеш `road_dist_cache.json`
  совместим с форматом v2 и читается без `eval`.

**Карта по дорогам** (`road_geometry.py`). Для каждого дня менеджера
выполняется один запрос OSRM Route API по цепочке «старт → точки в
порядке `order_in_route` → старт». Ответ разбивается на участки,
поэтому обход кластера и подъезды рисуются по-разному. Разворот в точке
разрешён (`continue_straight=false`), как и в матрице, по которой строился
план, поэтому км на карте совпадают с планом (1482 = 1482 км обхода).
Ответы кешируются в `cache/osrm_cache.json`, км и минуты по участкам
сохраняются в `road_stats.csv`.

Граф из v2 (`../cache2/volga_graph.graphml`, 1,5 ГБ) можно использовать
так:

```bash
python run.py --distance road --graphml ../cache2/volga_graph.graphml
```

Чтение графа такого размера через networkx занимает несколько минут и
требует много памяти. Чтобы построить граф заново:
`python -m src.download_pbf`, затем `src.distances.build_graph_from_pbf`
(нужен `pyrosm`).

## Выходные данные и их интерпретация

| Файл | Содержание |
|---|---|
| `schedule.csv` | **итоговая таблица ТЗ**: `point_id, visit_day, cluster_id, order_in_route` + `manager, cluster_seq_in_day, visit_number, visits_per_month, latitude, longitude` |
| `clusters.csv` | кластер дня: число точек, длина обхода, подъезд/возврат, оценка часов |
| `daily_stats.csv` | загрузка менеджера по дням: кластеры, визиты, км, часы, превышение нормы |
| `territories.csv` | территория и первый день каждой точки |
| `unassigned.csv` | визиты, которые не удалось поставить, с причиной (дефицит) |
| `rejected_rows.csv` | отклонённые строки входа с причиной |
| `checks.csv` | проверки плана по критериям приёмки ТЗ |
| `report.json` | параметры запуска, источник расстояний, итоговые счётчики |
| `route_map.html` | интерактивная карта, линии по дорогам |
| `road_stats.csv` | км и минуты по дорогам на кластер: обход (`road_*`) и подъезд/переезд/возврат (`transfer_*`) |

Как читать `schedule.csv`: строка — один визит. `visit_day` — рабочий
день (1..22). `cluster_id = M{менеджер}-D{день}-T{территория}` — маршрут
менеджера в этот день. `order_in_route` — номер точки в обходе.
`cluster_seq_in_day` — какой по счёту это кластер у менеджера в этот день.
`visit_number / visits_per_month` — например, «2 из 2».

**Карта.** Каждый день каждого менеджера — отдельный слой (панель справа,
сгруппировано по менеджерам). Цвет точки и линии обозначает кластер дня,
цифра в кружке — `order_in_route` из `schedule.csv`. Сплошная линия
соединяет точки строго в этом порядке. Пунктир — подъезд от старта,
переезд между кластерами и возврат. В слое «Все точки» цвет обозначает
менеджера. Линии идут по дорогам, в подсказке к линии указаны км и минуты.
Легенда выведена на карте, в ней же написано, как построены линии.

## Результат на `data/data.csv`

633 точки, 3 менеджера, 141 точка × 1 визит + 492 точки × 2 визита =
**1125 визитов**.

| Показатель | v2 | v3 |
|---|---|---|
| Назначено визитов | 777 из 1125 | **1125 из 1125** |
| Точек без единого визита | 85 | **0** |
| Потеряно визитов | 348 (молча) | **0** |
| Макс. точек в кластере | 12 | 12 |
| Кластеров у менеджера в день | 1 | ≤ 2 |
| Интервал между визитами точки | не контролировался | ровно 11 дней |
| Пробег за месяц по дорогам (3 менеджера) | — | ≈ 6 320 км |
| Расстояния в плане | прямая / граф | по дорогам (OSRM) |


Информативная проверка «день ≤ 9 ч» не проходит для 6 дней из 65. Это
выезды к территориям в 110–190 км по дорогам от Нижнего Новгорода:
при средней скорости 50 км/ч однодневный выезд из центра туда длится
9,2–12 ч. Решение зависит от бизнеса: другая точка старта
(`depot`) для удалённых менеджеров, командировка или более высокая
скорость на трассе.

## Ограничения и развитие

* Для > 5 000 точек у одного менеджера задача о назначениях в
  кластеризации станет медленной (O(n³)). Тогда стоит предварительно
  разбить точки на сектора или перейти на min-cost-flow.
* Время в пути — км по дорогам / средняя скорость. OSRM возвращает и
  длительность, её можно использовать вместо средней скорости.
* Публичный сервер OSRM — демонстрационный. Для регулярной работы лучше
  локальный OSRM с тем же API.
* Не учитываются временные окна точек и праздничные дни (visit_day —
  номер рабочего дня, а не дата).
